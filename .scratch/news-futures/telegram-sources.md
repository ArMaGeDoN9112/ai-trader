# Telegram: источники и непрерывный приём

Проверено 2026-11-06 по первичным источникам. Аккаунты не подключались. После исследования пользователь в Q26 подтвердил наличие разрешения на AI-обработку MarketTwits и РБК; ниже описаны опубликованные условия и технические варианты, а не сохраняющийся запрос на подтверждение прав.

## Первые каналы

- [@markettwits](https://t.me/markettwits) открывается как MarketTwits; доступен [публичный просмотр](https://t.me/s/markettwits).
- [@rbc_news](https://t.me/rbc_news) открывается как «РБК. Новости. Главное», с отметкой верификации и описанием официального канала РБК; доступен [публичный просмотр](https://t.me/s/rbc_news).

Preview содержит отметки редакций; у РБК часть элементов предлагает открыть Telegram. Полнота медиа и журнал изменений не гарантированы. Вывод: ссылки доступны, но надёжность непрерывного приёма через HTML с восстановлением не установлена.

## Два официальных способа

**Bot API.** Бот получает сообщения каналов, участником которых является: буквальное условие [FAQ](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get). Добавление бота владельцами этих каналов не предполагается. Токен не даёт подписку на произвольный username. [joinChannel](https://core.telegram.org/method/channels.joinChannel) и [getHistory](https://core.telegram.org/method/messages.getHistory) доступны только пользователям; Bot API не имеет общего чтения истории.

Доступны `channel_post` и `edited_channel_post` известных боту публикаций. Доставка — long polling либо webhook; очередь хранится максимум 24 часа. `update_id` общий для бота; offset подтверждать после сохранения. Webhook не даёт доступа к чужому каналу или неограниченного восстановления. [Bot API](https://core.telegram.org/bots/api#getting-updates)

**Пользовательский MTProto-клиент.** Нужны собственные `api_id`/`api_hash`, авторизация пользователя и сохранённая сессия. Токен BotFather её не заменяет. Способ входа ещё не выбран. [Регистрация](https://core.telegram.org/api/obtaining_api_id), [авторизация](https://core.telegram.org/api/auth)

Username разрешается через [resolveUsername](https://core.telegram.org/method/contacts.resolveUsername). Пользователь вступает через joinChannel с учётом ограничений доступа/числа каналов. getHistory с пагинацией по ID/дате даёт доступную историю для backfill, не полный журнал редакций.

Есть updates новых/изменённых/удалённых сообщений. Состояние: общий `seq/date/pts/qts` сессии и `pts` каждого канала. На старте — `updates.getDifference`, затем нужные `getChannelDifference` по `updateChannelTooLong`, с применением промежуточных состояний. `last_message_id` недостаточен: ID редакции прежний. Для публичных каналов без вступления описан short polling при открытом просмотре, максимум десять одновременно; безлимитный опрос множества каналов из этого не следует. [Обновления](https://core.telegram.org/api/updates)

`channelDifferenceTooLong`: часть updates уже удалена из message box; каждую редакцию восстановить нельзя. getHistory не заменяет заполнение gaps журнала. Неполноту фиксировать явно. [TooLong](https://core.telegram.org/constructor/updates.channelDifferenceTooLong), [Updates](https://core.telegram.org/api/updates)

## Условие для использования в LLM

[API Terms §1.5](https://core.telegram.org/api/terms) распространяет ограничение на использование данных Telegram для AI/ML, включая «deployment». Связанные [Content Licensing, раздел Large Language Models and AI](https://telegram.org/tos/content-licensing) запрещают scraping, индексацию, сбор, агрегацию и использование таких данных для перечисленных целей AI/ML. Исключения *могут* предоставляться при индивидуальном явном, информированном и продолжающемся согласии всех относящихся к делу пользователей на конкретный контент и контекст; согласие не переносится на другие каналы.

Это шире обучения. Инженерный вывод: inference нельзя считать разрешённым по умолчанию; публичность, добавление бота и HTML-сбор сами разрешения не дают. Пользователь отдельно подтвердил наличие разрешения для двух выбранных каналов в Q26. Исследование не проверяло документы разрешения; повторное подтверждение для этих каналов не запрашивается.

## Предложение контракта

Адаптер на **тип источника**, конфигурация на канал: `telegram_user` с двумя начальными entries; следующий канал не требует нового парсера. `telegram_bot` — при согласованном добавлении владельцем. Будущие API/RSS/сайты дают тот же выходной контракт, извлечение определяется позже.

Выход: `source_id`, внешний ID публикации, URL, `published_at`, `edited_at`, `observed_at`, `new/edit/delete`, текст/подпись, ссылки, признак недоступного содержимого. Telegram-ключ — `(channel_id, message_id)`; username изменяем. Редакции сохраняются отдельно; транспортный дубль отличается от повторной публикации о событии.

Контракт адаптера: `resume(saved_state) → изменения + next_state`; первоначальный `backfill` имеет отдельную границу. Состояние MTProto включает общий cursor сессии и отдельный `pts` источника, Bot API — общий `update_id` бота, а не искусственный cursor на канал. Публикацию/редакцию, следующий cursor и задание обработки сохранять атомарно; подтверждать доставку после этого. После сбоя повтор доставки безопасен благодаря уникальному ключу изменения; очередь анализа продолжает работу независимо от подключения.

Это наш дизайн. Спорное совпадение событий сохраняется; существенная редакция может повторно запустить анализ компании. Поток: архив → сопоставление событий/маршрутизатор (Jev — кандидат) → аналитик компании → критик; риск контролирует код. Polling/reconnect обслуживают доставку, таймеры сами не запускают LLM.

Не выбраны библиотека, глубина backfill и обработка медиа. Разрешение на AI-обработку двух начальных каналов подтверждено пользователем. Сессии/ключи хранить локально вне репозитория/логов/LLM-входов. Лимиты, задержка и восстановление на аккаунте не проверялись; уже утраченные источником редакции архив не восполнит.
