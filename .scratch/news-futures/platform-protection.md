# Защитное закрытие на стороне T-Invest

Проверено 2026-11-06 по публичной документации T-Банка. Исследование для проекта; счета, токены и торговые методы не вызывались.

## Подтверждено

Стоп-заявка при выполнении условия превращается в биржевую заявку; действует до отмены или даты. Защита должна быть заранее принята платформой. Архитектурный вывод: достижение цены обслуживает инфраструктура брокера; до активации это ещё не биржевая заявка. Отдельного SLA для отключённого клиента документация не даёт. [Описание стоп-заявок](https://developer.tbank.ru/invest/services/stop-orders/head-stoporders).

Есть `STOP_LOSS`, `TAKE_PROFIT`, `STOP_LIMIT`, раздельные `stop_price` (активация) и `price` (дочернее поручение). `exchange_order_type` в gRPC-схеме описан именно для тейк-профита: market или limit. Возможность выбора дочернего типа для остальных стопов требует проверки. [Схема стоп-сервиса](https://developer.tbank.ru/invest/services/stop-orders/stoporders).

Цена активации не гарантирует цену закрытия: рыночное поручение может исполняться по нескольким худшим ценам; лимитное исполняется по указанной цене или лучше, но исполнения может не быть. Поэтому ограничение убытка в рублях — целевой расчёт защиты, а не обещанный максимум фактического убытка. [FAQ заявок](https://developer.tbank.ru/invest/services/orders/faq_orders), [ошибки исполнения и торговой сессии](https://developer.tbank.ru/invest/intro/developer/error-codes/errors).

Фьючерсы предусмотрены схемой стопов: `priceType` допускает пункты для фьючерсов. Доступность конкретного контракта ещё надо проверить. Есть расхождение: общая таблица описывает вход `PostStopOrder` в валюте расчётов, схема содержит выбор `price_type`. Единицы цены и округление требуют проверки. [PostStopOrder](https://developer.tbank.ru/invest/api/stop-orders-service-post-stop-order), [таблица цен](https://developer.tbank.ru/invest/intro/useful-info/points).

| Возможность | Песочница | Реальный контур |
|---|---|---|
| Стоп-сервис | Да | Да |
| Выставление, чтение, отмена стопов | Post/Get/CancelSandboxStopOrder; либо сервис на sandbox endpoint | Post/Get/CancelStopOrder |
| Реальное биржевое исполнение | Нет, эмуляция | Да, после активации и принятия дочернего поручения |

Источники: [различия контуров](https://developer.tbank.ru/invest/intro/developer/sandbox/url_difference), [SandboxService](https://developer.tbank.ru/invest/intro/developer/sandbox/methods), [алгоритм песочницы](https://developer.tbank.ru/invest/intro/developer/sandbox). Утверждение «в sandbox нет стопов» устарело. Песочница упрощает исполнение: встречного предложения на один лот может хватить для всего объёма; реальную ликвидность она не проверяет.

MCP заявляет стоп-заявки и sandbox URL. Публичное описание не перечисляет схемы инструментов: равенство MCP и gRPC, доступность всех полей и статусов ещё не доказаны. [T-Invest MCP](https://developer.tbank.ru/invest/mcp).

## Следствия для жизненного цикла

Это рекомендации проекта, а не дополнительные гарантии API:

1. Защищать фактически исполненный объём, включая частичные исполнения. API содержит `PARTIALLYFILL`, исполненные и оставшиеся лоты. [Схема заявок](https://developer.tbank.ru/invest/services/orders/methods).
2. Хранить ID стопа и сверять состояние и параметры на платформе. Неподтверждённая защита блокирует входы и запускает заданную аварийную процедуру без LLM. После активации проверить дочернюю заявку и остаток позиции; API возвращает `exchange_order_id`. [FAQ стопов](https://developer.tbank.ru/invest/services/stop-orders/faq_stoporders).
3. После TP, ручного или новостного полного закрытия сверять остаток, обычные заявки и стопы. Старый противоположный стоп потенциально может открыть обратную позицию. Сначала отменить защиту — появляется окно без защиты; сначала закрыть — появляется гонка двух выходов. Один лишь порядок вызовов эту проблему полностью не решает.

В прочитанных публичных схемах PostOrder/PostStopOrder нет подтверждённых `reduce-only`, OCO или атомарного «вход + защита». Нельзя обещать автоматическое снятие парного стопа и невозможность разворота. До выяснения нельзя считать две независимые заявки SL/TP безопасным автономным OCO.

## Открытые проверки интеграции

- Снять фактический список и схемы MCP-инструментов: фьючерсы, stop types, единицы цены, idempotency, чтение/отмена стопов, дочерние заявки и статусы. Отдельно проверить активацию после отключения клиента в sandbox; это проверка сценария, а не SLA production.
- Подтвердить конкретный фьючерс, SL/TP semantics, поведение при частичном исполнении и внешнем закрытии; уточнить у брокера native OCO/reduce-only. Реальный запуск не должен опираться на предположение об их наличии.
- Проверить восстановление после таймаута/рестарта и гонку «стоп активируется одновременно с новостным выходом». Для входа и стопа использовать устойчивые идентификаторы запросов; отсутствие ответа не означает отсутствие поручения.

Одна позиция, размер входа и свежесть данных проверяются программным контуром. Дневное ограничение убытка в текущем прототипе не используется: пользователь отменил его в Q41. Брокерские ограничения стоимости заявки и ГО — другие проверки; пользовательский account-wide/day-loss kill switch в просмотренной документации не найден. [FAQ заявок](https://developer.tbank.ru/invest/services/orders/faq_orders), [ГО фьючерсов](https://developer.tbank.ru/invest/services/instruments/head-instruments).

Для проекта: ценовой стоп независим от агентов; новостной полный выход одобряют аналитик компании и критик. Неопределённость исполнения блокирует входы. Long/short/skip при flat и hold/полное закрытие при позиции не отменяют учёт частичных исполнений.
