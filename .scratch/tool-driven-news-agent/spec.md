# Агент с инструментами для анализа новостей

Status: needs-triage

## Гипотеза и границы эксперимента

На новой редакции публикации модель сама решает, какие данные ей нужны, в каком порядке их получить и когда остановиться. Для явно нерелевантной новости хватит пропуска; для спорного обновления агент может прочитать новостной контекст компании, проверить котировку, спросить критика и вернуться к поиску. Цель — выяснить, даёт ли этот выбор лучшее решение при приемлемых задержке и стоимости.

Первый результат — структурированный пропуск или торговое предложение с проверяемыми источниками и трассой решения. Режим эксперимента не получает пишущий брокерский клиент. Выставление заявки проверяется отдельно и только в песочнице после сравнения маршрутов. Текущий пайплайн остаётся контролем.

## Что происходит сейчас

| Участок | Текущее поведение и его следствие |
| --- | --- |
| Вход | [Runtime.process_revision](../../news_futures/application/runtime.py#L180) получает редакцию из очереди, фиксирует входы и вызывает `analyze_news`. Готовность брокера сейчас может задержать даже начало анализа. |
| Привязка | [workflow.py](../../news_futures/application/workflow.py#L141) задаёт `route → event → snapshot → review`. Категория и Jev сужают список компаний, архив событий регистрирует привязки и обновления. Агент не может попросить другой источник или пересмотреть выбор компании. |
| Контекст | [prepare_context](../../news_futures/agents/decisions.py#L72) заранее подбирает рынок, счёт и связанный новостной контекст в пределах лимита. Модель не задаёт уточняющий запрос, если в этом наборе чего-то не хватает. |
| Роли | [review_cycle](../../news_futures/agents/review.py#L238) запускает аналитика, затем критика и при необходимости допускает одну ревизию. [read_approval](../../news_futures/agents/approval.py#L14) проверяет конкретный формат сохранённой пары «предложение аналитика / ответ критика». Это часть интерфейса исполнения. |
| Эффект | [Runtime._execute_review](../../news_futures/application/runtime.py#L291) вызывает `SandboxExecutor` после анализа. Исполнитель владеет лимитами риска, резервированием, отправкой, защитой и сверкой. MCP в текущем репозитории используется для [диагностики чтением](../../docs/sandbox.md); рабочий адаптер заявок использует [Sandbox REST](../../docs/sandbox-execution.md#L60). |

## Целевой цикл

Один ведущий агент вместо обязательной цепочки ролей. Использовать существующий LangGraph, текущий совместимый чат-адаптер и Pydantic. Код управляет переходами и полномочиями, модель выбирает следующий допустимый шаг. Критик — один структурированный вызов модели внутри инструмента со своим бюджетом и без доступа к инструментам.

```text
Редакция → проверка пригодности и регистрация события
         → модель ⇄ разрешённый инструмент → пропуск / проверенное предложение
                                                         ↓
                                [отдельный этап] допуск → исполнитель → сверка
```

- Точка замены — внутри `analyze_news`, после регистрации события. Оставить категорию/Jev и сопоставление событий на первом этапе, чтобы сравнение меняло только стратегию анализа. Проверки свежести редакции, повторов, разрешённых компаний и политики открытой позиции остаются в коде. Вторым опытом можно сделать привязку к компании инструментом, если разбор пропусков покажет потери на ранней маршрутизации.
- На старте дать модели публикацию, событие и компактный перечень разрешённых кандидатов. Существующие `Snapshot` и `CompanyContext` использовать как типы для проверок, но собирать контекст модели из фактически полученных наблюдений. Отделить поиск от `prepare_context`, чтобы скрытый обязательный сбор всего контекста не вернул прежний конвейер. При недоступном брокере локальный разбор может закончиться пропуском или «данных недостаточно»; рыночное наблюдение и допуск требуют свежих данных.
- LangGraph хранит редакцию, ID запуска, сообщения, выданные наблюдения, зафиксированные для запуска версии модели, промпта и инструментов, остаток бюджета и итог. Для эксперимента использовать отдельное пространство артефактов и checkpoint ID с вариантом и версией графа. Возобновление проверяет редакцию, снимок и бюджет; просроченный запуск закрывается, старое предложение не становится новой заявкой. Отмена прекращает новые вызовы.
- Стартовые лимиты для наблюдения: 6 ходов ведущей модели, 5 вызовов инструментов последовательно, из них максимум 2 вызова критика, и общий дедлайн 45 секунд. Это оставляет место для двух запросов новостей, котировки и повторной проверки критиком. Перед каждым вызовом проверять остаток времени и бюджета токенов; стартовый лимит — 24 тыс. входных и 4 тыс. выходных токенов суммарно, включая критика. Тайм-аут инструмента — не более 10 секунд и не больше остатка общего дедлайна. Повтор идентичного запроса возвращает прежнее наблюдение; при отсутствии прогресса, исчерпании лимита или невалидном итоге — завершение с причиной и без заявки. Эти числа подлежат калибровке на первом наборе.

## Инструменты и полномочия

| Инструмент | Контракт и правила |
| --- | --- |
| `get_company_news(company_id, query?)` | Читает локальный новостной контекст из `EventArchive.report`. Только компании из разрешённого списка кандидатов, до 8 записей и заданного лимита байт. Выдаёт ID редакции и события, время, источник, текст и признак повтора/опровержения. При повторном прогоне читает только данные, известные к моменту решения, включая версии исправлений. Пустой ответ, запрет и сбой различаются. |
| `get_market_context(contract_id)` | Читает котировку, статус сессии и необходимую часть состояния счёта через существующий адаптер чтения или из записанного снимка. Счёт выбирает приложение. Возвращает время, единицы и статус свежести; просроченный снимок не допускает предложение к исполнению. |
| `ask_critic(proposal)` | Проверяет форму предложения и собирает доступные ему доказательства по ссылкам из состояния запуска. Возвращает структурированное заключение `Review` с ID предложения, решением и возражениями. Любое изменение параметров или проверяемого контекста аннулирует заключение. Для пропуска вызов не нужен; кандидат на передачу исполнителю требует положительного заключения для точной версии. Отдельный «инвестор» позже, если в тестах обнаружится вопрос, на который критик не отвечает. |
| `request_entry(proposal_id)` | Только на этапе проверки исполнения. Ссылается на сохранённое, прошедшее проверку предложение `enter`; не принимает счёт, произвольную сумму, endpoint или имя MCP-инструмента. Вызов создаёт запрос на исполнение и завершает модельный цикл. Подтверждение исполнения возвращает программный контур по данным брокера: запрос, заявка, исполнение и защищённая позиция — разные статусы. |

Запуск выбирает из закрытого списка инструментов. Приложение проверяет имена, схемы, связи «компания ↔ контракт», допустимость действия и цитаты по фактически выданным редакциям. Новостные тексты и ответы инструментов — входные данные; содержащиеся в них команды не меняют права, политику или конфигурацию. Не выдавать модели токены, сессии, произвольный доступ к SQL, URL или сырому MCP. Сохранять только нужные для проверки поля; для модели — минимальный контекст счёта, для трассы — идентификаторы и проверяемые результаты.

На этапе песочницы оператор подтверждает конкретную версию предложения (счёт, контракт, направление, объём, уровни, срок действия). Исполнитель повторно проверяет актуальность публикации, рынок, состояние счёта, паузу новых входов и риск. Размер заявки рассчитывает код. Для повтора использовать существующее резервирование и журнал со стабильным ключом операции; если ответ на отправку потерян, сначала сверить состояние брокера. Неизвестный исход блокирует повтор и новые входы до сверки. Ручное закрытие, сопровождение позиции и аварийные действия остаются в действующем контуре.

Требование «через MCP» — отдельная проверка адаптера под интерфейсом [SandboxBroker](../../news_futures/trading/broker.py). Наличие инструмента отправки заявки недостаточно: нужны подтверждённые семантики Sandbox, идемпотентность входа и защиты, наблюдаемость заявок и исполнений, безопасная отмена и восстановление при неопределённом исходе. Нынешняя проверенная схема MCP не обеспечивает все требования; в REST-пути автономный вход тоже блокируется при независимых SL/TP без ручного opt-in. Для проверки гипотезы использовать тестового брокера, а при неподтверждённой защите оставить песочницу в действующем режиме. Не менять флаг допуска ради опыта.

## План переработки

1. **Зафиксировать базу и набор сравнения.** Собрать не менее 30 размеченных редакций из архива: очевидный пропуск, релевантное событие, спорная косвенная связь, повтор, опровержение, правка во время обработки, нехватка данных. Отдельно держать примеры с открытой позицией для проверки текущей политики. Заморозить каталог, модели, архив и снимки по состоянию на момент каждой редакции, чтобы обе схемы видели одни данные. Снять текущие решения, задержку и стоимость.
2. **Добавить цикл в режиме наблюдения.** Подключить отдельный вариант `tool_agent` в конфигурации анализа, независимый от режима брокера, с запретом его запуска с пишущим брокером на первом этапе. Реализовать три первых инструмента, единый диспетчер и выход `skip / candidate / insufficient_data / failed`. Сохранить отдельную версию графа, не мигрировать старые checkpoint. Проверить через существующую точку обработки ревизии в `tests/application/test_runtime.py` с подменёнными моделью, новостями и снимком; не использовать сеть в регрессионных тестах. Для первого прогона выбрать одну комбинацию чат-модели и провайдера и отдельно проверить полный обмен `tool_call → ToolMessage → ответ` на закреплённых версиях. Поддержка `json_schema` в текущих моделях сама по себе этого не доказывает.
3. **Показать и сравнить решения.** Сохранять по каждому вызову: редакцию, ID запуска и вызова, имя, проверенные аргументы, статус, ссылки на данные, время, версию модели/промпта и доступные токены/стоимость. Вначале достаточно `runtime-status --decision`; если эксперимент продолжается, добавить последовательность инструментов в [trace_view](../../news_futures/operator/news.py#L362) и панель, сохранив чтение старых трасс. Сравнивать на одинаковых редакциях и по слепой разметке; не считать кэшированный прогон за оценку реальной задержки. Если выигрыша нет, оставить текущий маршрут и изучить пропуски по трассам.
4. **При выигрыше проверить исполнение с тестовым брокером.** Добавить `request_entry` и проверяемую передачу подтверждённого предложения в существующий исполнитель. Текущий `read_approval` ожидает артефакты старого графа; не подделывать пару файлов аналитика и критика. Выделить предметный формат проверенного предложения с версией, хешем, временем и заключением критика; старый читатель приводит старые артефакты к тому же формату. Проверить риск, журнал, защиту, потерянный ответ, перезапуск, параллельные дубли, паузу и неизменность ручного закрытия. Отдельным решением проверить совместимость MCP; подключать его к исполнителю только при подтверждении всех свойств из предыдущего раздела.

## Приёмка и решение о продолжении

| Сценарий | Что должно быть видно |
| --- | --- |
| Простая новость | Агент завершает пропуск без обязательного вызова котировки и критика. |
| Неясное влияние | Агент вызывает поиск и использует выданную редакцию. При возражении критика может уточнить запрос и пересмотреть предложение; прежнее заключение не подходит к новой версии. |
| Повтор, старая редакция, выдуманная цитата, подмена инструмента из новости | Пригодность редакции проверяет код; подложная ссылка/цитата не проходит валидацию; запись у брокера отсутствует. |
| Тайм-аут, отказ модели, пустая выдача, недоступный брокер | В трассе различимы причины. Локальный анализ может завершиться, но отсутствие необходимых данных не превращается в подтверждённый вход. |
| Восстановление или откат на текущий граф | Варианты не подхватывают чужие checkpoint и предложения. Сопровождение уже открытых позиций остаётся за действующим исполнителем. |
| Этап тестового исполнения: дубль или потерянная квитанция | Не более одной заявки на намерение; результат получен сверкой, либо цикл блокируется с явной причиной. |

Предлагаемый порог для продолжения: ни одного нарушения инвариантов; доля решений, прошедших рубрику (компания, корректная опора на источники, действие или обоснованный пропуск), не ниже текущего маршрута на всей выборке и минимум на 10 п.п. выше на неоднозначных новостях; p95 задержки и средняя стоимость одной редакции — не выше 1,5× базы. Простые случаи должны показывать меньше лишних вызовов, сложные — хотя бы один наблюдаемый пример уточнения по результату инструмента. Пороги зафиксировать до оценки; небольшой набор служит фильтром для продолжения эксперимента, выводов о доходности он не даёт.

[ADR 0001](../../docs/adr/0001-separate-proposals-from-execution.md), [ADR 0002](../../docs/adr/0002-langgraph-langchain-agent-workflows.md) и [ADR 0003](../../docs/adr/0003-local-operator-control.md) сохраняются. Перед переводом эксперимента в основной режим нужно обновить [agent-stack](../../docs/agents/agent-stack.md): политика сейчас закрепляет маршрут и набор ролей. Уточнить модель для первого теста по фактической поддержке вызовов; вопрос замены REST на MCP решать после проверки возможностей, независимо от результата A/B.
