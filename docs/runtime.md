# News-futures: основное руководство

Приложение отслеживает новости Telegram и сохраняет решения по фьючерсам. Путь редакции: категория и компании → событие и проверка позиции → выбор серии → анализ и проверка критиком. Связь новости с компанией сама по себе не даёт сигнала на вход.

Это руководство по устройству, эксплуатации и проверке проекта.

## Запуск

Для существующей установки сначала выполни подходящую миграцию из разделов ниже. Команды Docker выполняются из корня репозитория.

Понадобится Docker с Compose. Из корня проекта скопируй [шаблоны](../config/) и [шаблон ключей](../credentials.example.toml) в `.local` без суффикса `.example`, если этих файлов ещё нет. Заполни ключи Telegram, OpenRouter или Groq и песочницы согласно профилю. Один раз авторизуй Telegram в контейнере. Если каталога брокера ещё нет, выполни диагностику:

~~~powershell
docker compose build backend
docker compose run --rm backend telegram-login
docker compose run --rm backend sandbox-diagnostics .local/catalog --config .local/sandbox-settings.json
~~~

Укажи `account_id` из отчёта диагностики в `.local/runtime.json`. Если переходишь с локального запуска Python, сначала останови прежний обработчик. Выполни `docker compose up --build -d`, открой [127.0.0.1:8765](http://127.0.0.1:8765/) и нажми **Запустить**. Контейнер бэкенда запускает API; обработчик остаётся остановленным до команды из панели.

Фронтенд обслуживает Nginx и передаёт запросы `/api/` во внутреннюю сеть Compose. Бэкенд видит хостовую папку `.local` как `/app/backend/.local`. Храни там профиль, сертификаты и JSON-артефакты. Используй относительные пути в профиле. Оставь поле `session` незаданным, чтобы Compose хранил сессию Telegram в томе `telegram`. База доступна внутри Compose. При первой инициализации пароль можно задать через `TRADER_POSTGRES_PASSWORD`. Команда `docker compose down` сохраняет тома, а флаг `-v` удаляет базу и сессию.

Для остановки стека используй `docker compose down`, для журналов — `docker compose logs -f backend frontend`. После правок файлов рабочего профиля перезапусти бэкенд командой `docker compose restart backend` и обнови вкладку.

## Панель и обработчик в Windows

Для доступа к OpenRouter через VPN Windows оставь PostgreSQL в Compose и запусти панель и обработчик на хосте. Из корня проекта установи Python-зависимости в `.venv` командой `python -m pip install -r backend/requirements.txt`, затем установи зависимости фронтенда через `npm.cmd --prefix frontend ci`. Для Telegram используется локальная сессия Windows. Команда `telegram-login` из корня проекта ищет Python-пакет через `$env:PYTHONPATH = (Resolve-Path .\backend).Path`.

Запусти `pwsh -NoProfile -File .\run-local.ps1`. Скрипт соберёт фронтенд, остановит контейнеры панели и бэкенда, откроет существующую базу на `127.0.0.1:55432` и поднимет панель на [127.0.0.1:8765](http://127.0.0.1:8765/). Запусти обработчик из панели. Чтобы вернуться к запуску всего стека через Compose, сначала останови локальную панель сочетанием `Ctrl+C` в её терминале и выполни `docker compose up --build -d`.

Панель и обработчик — разные процессы. **Остановить** в панели завершает worker, но оставляет API доступным. Закрытие вкладки не останавливает worker. Смена режима требует остановки обработчика и подтверждения отсутствия позиции и операций. Список источников применяется после перезапуска worker; изменения чат-моделей — к следующей редакции. Для штатной остановки локальной панели используй `Ctrl+C` в терминале `run-local.ps1`.

## Хранение и резервные копии

| Место | Содержимое |
| --- | --- |
| `.local/runtime.json` | Профиль установки; относительные пути считаются от него |
| `.local/credentials.toml` | Секции `telegram`, `openrouter`, `groq`, `sandbox` из [шаблона](../credentials.example.toml) |
| `data_dir/decisions/<revision>/` | Исходная публикация, замороженные входы, результаты этапов, наблюдения, кандидаты и трассы |
| PostgreSQL | Публикации и курсоры, очередь, события, торговый журнал, настройки оператора и checkpoints |
| Том `telegram` / локальная сессия Windows | Авторизация Telegram соответствующего способа запуска |
| `backend/news_futures/defaults/` | Комплектные JSON для новых запусков; копии входов старых редакций остаются в их артефактах |

PostgreSQL использует отдельные схемы для архивов `publications`, `events`, `operator`, `checkpoints`. Имя схемы вычисляется из persistent path. `.local` на Windows и `/app/backend/.local` в Compose связывает `TRADER_CONTAINER_LOCAL`; изменение `data_dir` или этого отображения открывает другой набор схем.

Перед обновлением останови API, worker и ручные sandbox-команды. Сохрани дамп PostgreSQL командой `pg_dump --format=custom` и копию `.local`, включая артефакты и локальные сессии. Для контейнерной Telegram-сессии сохрани также том `telegram`. Проверь архив и восстановление дампа в отдельную базу. Копии `.local` содержат ключи и сессии; они должны оставаться вне Git.

При откате останови процессы и восстанови совместимые версии кода, базы и `.local` вместе. Старый код не должен читать уже перенесённые пути типов. Не удаляй таблицы, checkpoints или торговый журнал для обхода ошибки восстановления.

## Переход с SQLite

Из корня проекта останови панель, обработчик и любые отдельные команды, которые пишут в старые архивы. Затем выполни:

~~~powershell
docker compose stop frontend backend
docker compose build backend
docker compose run --rm backend migrate-sqlite .local/runtime.json
docker compose up -d
~~~

Команда ищет SQLite-файлы в `data_dir` профиля и выводит число перенесённых строк. Она переносит публикации и курсоры, историю событий и сделок, состояние оператора и чекпоинты LangGraph. Старые файлы остаются на месте. Запуск с ними требует успешно завершённого импорта. Для существующего профиля используй тот же путь `data_dir` внутри контейнера.

## Обновление структуры Python-пакета

При переходе со структуры `domain / application / adapters / bootstrap` сохрани прежние `data_dir`, `.local`, `TRADER_CONTAINER_LOCAL` и Docker mount `/app/backend/.local`: от persistent path зависит имя схемы PostgreSQL. Старые Python-импорты больше не поддерживаются.

Останови API, worker и отдельные команды `sandbox-trade`. Сохрани согласованные резервные копии PostgreSQL и `.local`; сначала проверь обновление на их копии. После сборки нового кода выполни миграцию с прежним профилем и теми же путями:

~~~powershell
docker compose stop frontend backend
docker compose build backend
docker compose run --rm backend migrate-checkpoints .local/runtime.json
docker compose up -d
~~~

Для Windows после остановки локальной панели используй прежнее окружение запуска: `DATABASE_URL`, пароль базы, `PYTHONPATH` и `TRADER_CONTAINER_LOCAL`. Из корня проекта выполни `.\.venv\Scripts\python.exe -m news_futures migrate-checkpoints .local/runtime.json`, затем запусти `run-local.ps1`.

У локального запуска переменные можно подготовить так; пароль остаётся в окружении процесса и не печатается:

~~~powershell
$env:PYTHONPATH = (Resolve-Path .\backend).Path
$env:TRADER_CONTAINER_LOCAL = '/app/backend/.local'
$env:DATABASE_URL = 'host=127.0.0.1 port=55432 dbname=trader user=trader'
$env:PGPASSWORD = docker compose exec -T postgres printenv POSTGRES_PASSWORD
try {
    .\.venv\Scripts\python.exe -m news_futures migrate-checkpoints .local/runtime.json
    if ($LASTEXITCODE -ne 0) { throw 'Checkpoint migration failed' }
} finally {
    Remove-Item Env:PGPASSWORD
}
~~~

Миграция меняет только пути типов внутри `checkpoint_blobs` и `checkpoint_writes` в одной транзакции. История checkpoints, thread IDs, namespace, версии, parent IDs, порядок writes и бизнес-таблицы сохраняются. Повторная команда не меняет уже перенесённые данные. Неизвестный тип прерывает миграцию с откатом; попытка читать старый тип до миграции явно требует `migrate-checkpoints`. Исторический `migrate-sqlite` сразу переводит типы в новые пути. При откате восстанавливай совместимые код и данные вместе.

## Рыночные наблюдения и replay

`get_market_context` передаёт статус сессии брокера вместе со стаканом. `get_event_versions` читает историю текущего события и редакции того же поста, показывает добавленные и удалённые фрагменты, ссылку на самое раннее сообщение в архиве и ссылки, указанные в публикациях. Такие ссылки помогают найти первоисточник. Инструмент не проверяет содержание внешних страниц.

`compare_market` сопоставляет доходности фьючерса, базовой акции и IMOEX от публикации и от получения новости. Сравнение требует общих минут закрытия свечей. Для финансов, потребительского сектора, нефти и газа, металлов и добычи бенчмарк подбирается по категории фьючерса. Поле `sector_benchmarks` в формате `{ "company_id": "UID инструмента" }` задаёт бенчмарк компании явно. Свечи фьючерса используют транспорт профиля, базовая акция и индексы читаются через REST.

`get_upcoming_events` показывает ближайшие события за 45 дней. В комплект входит сверенный календарь решений Банка России и выбранные раскрытия Московской биржи. Для расширения скопируй [файл календаря](../backend/news_futures/defaults/events-calendar.json) и укажи путь в `events_calendar` профиля. В `starts_at` укажи дату в московском календаре или точное время с часовым поясом. Корпоративные строки требуют `company_id` из каталога и ссылку на публикацию эмитента. Поддерживай `checked_on` при обновлении данных. Для каждой редакции рабочий цикл сохраняет копию календаря, использованную при анализе.

Пустая история инструмента отмечается в `missing_instruments`. Остальные серии сравниваются на общих минутах, доступных для них. `issuer_covered` отражает наличие событий эмитента в загруженном файле. Проверяй дату `checked_on` и покрытие перед интерпретацией пустого календаря.

Идентификаторы IMOEX и четырёх отраслевых индексов сверены с методом `Indicatives` песочницы Т‑Банка. Назначение отраслевых индексов опубликовано [Московской биржей](https://www.moex.com/ru/all-indices). Исходные расписания доступны у [Банка России](https://www.cbr.ru/dkp/cal_mp/) и в [календаре эмитента Московская биржа](https://www.moex.com/ru/about/investoram-i-aktsioneram/kalendar-investora).

Снимок рынка включает лучшие bid/ask, объём на обоих уровнях и время обновления стакана. Инструмент `get_market_context` также передаёт спред в пунктах и доступность заявок по сторонам. Инструмент `get_market_reaction` по запросу аналитика считает изменение цены и объём по завершённым минутным свечам отдельно от времени публикации и от времени получения новости. В отчёте указываются число свечей и объём относительно предыдущих пяти минут. Время границ задаёт приложение. Критик получает те же данные реакции, что и аналитик. Стакан и свечи читаются через REST в профиле `rest` и через подтверждённые инструменты sandbox MCP в профиле `mcp`. Проверки счёта и сверка исполнения читают REST.

Профиль задаёт `signal_timeout_seconds` (60 секунд по умолчанию). Срок считается от `received_at` и ограничивается максимальным возрастом публикации. Истёкшая редакция получает `signal_deadline`. В `runtime-status` сохраняются `queue_wait_ms`, `deadline_at` и общая `latency_ms`. Уже отправленные операции продолжают сверяться брокерским циклом.

Когда аналитик запрашивает рыночные данные, обработчик сверяет актуальность редакции и события параллельно с чтением рынка и ещё раз перед передачей снимка. Рыночное наблюдение сохраняется в `decisions/<revision>/market/<observation_id>.json`. Одобренный кандидат на вход в `decisions/<revision>/candidates/` ссылается на тот же снимок, который получил критик. Тестовые новости сохраняют результаты в трассах. Допуск и отправка заявки выполняются отдельной ручной командой песочницы.

Из `backend/` можно получить JSON-отчёт, передав каталог решений и отдельный файл котировок в формате JSON Lines. Каждая строка имеет ту же схему, что JSON-файл из каталога `market`.

~~~powershell
python -m news_futures replay ../.local/runtime/decisions --quotes history.jsonl --max-outcome-lag-seconds 5
~~~

У наблюдения укажи UID контракта, время последней сделки в `market.observed_at`, цену в `market.last_price`, время доступности записи в `received_at`, единицу `price_unit` (`points`) и булевы `limit_buy_available` и `limit_sell_available`. Нужны исходные времена доступности рыночных данных. Время экспорта файла для этого не подходит.

Отчёт покажет движение последней цены по направлению кандидата в базисных пунктах через 1, 5 и 15 минут после решения. Для каждого горизонта берётся первое доступное наблюдение со сделкой от целевого момента. Если наблюдение не уложилось в заданное окно, исход получает `missing_quote`. Это оценка реакции цены. Спред, комиссии и исполнение заявки в ней не учитываются.

## Настройки

- [Профиль](../config/runtime.example.json): режим, счёт, каталог, `data_dir`, интервалы и лимиты агента. Пути считаются от файла профиля; его правки требуют перезапуска.
- [Decisions](../backend/news_futures/defaults/decisions-model.json): один `model` для категорий, компаний и выбора фьючерса. По умолчанию `parallel/decisions-fast:free`; при ошибке запасная модель не вызывается. Для своего профиля скопируй файл в `.local` и укажи его в поле `decisions`. Панель отображает эту модель, а изменения в панели относятся только к чат-ролям.
- Чат-роли: [OpenRouter](../backend/news_futures/defaults/openrouter-models.json) или [Groq](../backend/news_futures/defaults/groq-models.json); отдельная модель координатора задаётся в `coordinator`. Модели фиксируются на редакцию, изменения применяются к следующей.
- Остальные справочники: [каналы Telegram](../backend/news_futures/defaults/telegram-sources.json), [категории фьючерсов](../backend/news_futures/defaults/futures-categories.json), [лимиты риска](../backend/news_futures/defaults/risk-policy.json).

| Поле профиля | Значение и смысл по умолчанию |
| --- | --- |
| `mode` | `observation`; `sandbox` разрешает только программный контур песочницы |
| `order_transport` | `rest`; `mcp` требует подтверждённых sandbox bindings |
| `chat_aggregator` | `openrouter`; `groq` относится к чат-ролям, Decisions остаётся отдельным контрактом |
| `signal_timeout_seconds` | 60 секунд от получения новости |
| `futures_refresh_seconds` | 86400 секунд между обновлениями каталога |
| `broker_refresh_seconds` | 15 секунд между сверками брокера |
| `agent_limits` | Лимиты ходов, чтений, бюджета и времени из [профиля](../config/runtime.example.json) |
| `events_calendar`, `sector_benchmarks`, `ca_file` | Свой календарь, UID отраслевых бенчмарков и сертификат при необходимости |

Штатная MCP-интеграция получает схемы инструментов у сервера при подключении. Фиксированных хешей описаний и схем в коде нет: изменения текста описания и совместимые расширения схем не блокируют вызов. Сохраняются проверка аргументов по текущей схеме, признак `readOnlyHint` для чтений и проверки необходимых данных ответа. Если обязательные параметры или данные стали несовместимыми, операция завершается ошибкой. Ручные `bindings` в настройках диагностики остаются явно заданным оператором контрактом.

Обязательны `data_dir`, `catalog`, `account_id`. Ключи читаются из `.local/credentials.toml`, а не из JSON профиля. Настройки строго валидируются; неверный ответ модели или недоступный источник не заменяются запасной моделью или выдуманными данными.

## Путь публикации и полномочия

Координатор делегирует разбор новости, а аналитик вызывает инструменты чтения архива и рынка в пределах назначенной компании и контракта. Для этой роли нужна модель с поддержкой вызова инструментов. Критик проверяет точную версию предложения; допускается одна доработка. Одобрение критика публикует торговое предложение.

`observation` читает брокера. Запись в песочнице доступна только отдельному исполнителю после независимых проверок риска. При неизвестном исходе исполнитель сверяет журнал и брокера перед любым повторным действием. Тестовые новости из панели не допускаются к исполнению.

Единица обработки — редакция публикации с устойчивым digest. Повторы, история и устаревшие редакции не должны порождать новый вход. Предложение привязано к конкретным публикации, контракту, версии события, снимку рынка и проверке критика. Размер позиции вычисляет код: комплектная политика задаёт максимум 500 ₽ планового риска и плечо 2; допустимый возраст новости — 900 секунд, предложения и риск-данных — 60 секунд. Ограничение сигнала дополнительно задаётся профилем.

При открытой позиции рабочий runtime пропускает новый новостной анализ до подтверждения выхода брокером. После рестарта отправленные операции сверяются по устойчивым идентификаторам, заполненному объёму и защите; неопределённый ответ не разрешает повторную отправку. Панель сохраняет состояние паузы отдельно от сверки уже отправленных операций. Ручное закрытие из панели — сохраняемый запрос исполнителю; успех подтверждается состоянием брокера, а не нажатием кнопки.

## Архитектура бэкенда

- [startup.py](../backend/news_futures/startup.py) подключает зависимости, [runtime.py](../backend/news_futures/runtime.py) ведёт очередь, [workflow.py](../backend/news_futures/workflow.py) выполняет граф обработки редакции. CLI, настройки, автономная симуляция и replay находятся в корне пакета.
- [agents](../backend/news_futures/agents/) содержит сценарии LangGraph, prompts, схемы команды и инструменты анализа; [llm_clients](../backend/news_futures/llm_clients/) — клиенты моделей и их контракты. Анализ получает только операции чтения рынка.
- [dataflows](../backend/news_futures/dataflows/) содержит Telegram, публикации и обработку сохранённых каталогов; [brokers](../backend/news_futures/brokers/) — интеграцию Т‑Банка и отдельные контракты чтения и отправки заявок.
- [trading](../backend/news_futures/trading/) содержит проверку approval, допуск, расчёт объёма, исполнение и сверку. [storage](../backend/news_futures/storage/) содержит PostgreSQL, checkpoints, миграции и контракты хранения. При сохранении резерва PostgreSQL удерживает блокировку записи до фиксации торгового намерения.
- [api](../backend/news_futures/api/) содержит HTTP-панель и управление отдельным процессом `news_futures.api.worker`. Общие типизированные контракты находятся в [schemas](../backend/news_futures/schemas/), комплектные JSON — в [defaults](../backend/news_futures/defaults/). Настройки каждой сохранённой редакции читаются из её собственных артефактов.

Контрольные точки LangGraph используют имена Python-классов; порядок перехода описан выше. Архивы публикаций и событий, журнал сделок и готовые отчёты используют прежние форматы.

## Основные команды

В Docker используй `docker compose run --rm backend <команда>`, для работающего API — `docker compose exec backend python -m news_futures <команда>`. На Windows из корня проекта используй `.\.venv\Scripts\python.exe -m news_futures <команда>` с окружением, описанным выше. Все аргументы доступны через `--help`.

| Команды | Назначение |
| --- | --- |
| `operator-api`, `serve`, `runtime-status` | Панель, отдельный обработчик и сохранённая диагностика |
| `telegram-login`, `telegram`, `publications` | Авторизация, приём и чтение архива Telegram |
| `sandbox-diagnostics`, `futures-catalog` | Чтение брокера и сохранение каталога |
| `route`, `event-match`, `event-correct`, `events` | Привязка компаний и история событий |
| `entry-reason` | Сохранение исходного основания позиции |
| `sandbox-trade`, `sandbox-trades` | Ручной sandbox-сценарий исполнения и журнал |
| `migrate-sqlite`, `migrate-checkpoints` | Явные миграции при остановленных процессах |
| `run`, `show`, `replay` | Автономная симуляция, чтение её трассы и оценка кандидатов |

`run / show` работают без сторонних библиотек и сетевых вызовов. Симуляция использует фиксированные ответы и не является живым анализом новостей.

## Диагностика и проверка

- Начни с `docker compose exec backend python -m news_futures runtime-status .local/runtime.json --decision ID` или трассы в панели. Трассы лежат в `data_dir`, а контрольные точки в PostgreSQL привязаны к абсолютному пути этого каталога внутри контейнера.
- Аргументы команд доступны через `docker compose run --rm backend <команда> --help`.
- Панель работает на FastAPI и Uvicorn. SQLAlchemy Core обслуживает транзакции приложения в существующих схемах PostgreSQL. LangGraph использует драйвер psycopg для контрольных точек.
- Образ бэкенда устанавливает [requirements.txt](../backend/requirements.txt). Файл [constraints.txt](../backend/constraints.txt) фиксирует версии для Docker и локальной установки.
- Для тестов выполни `python -m pip install -r requirements-dev.txt` из `backend/` в окружении Python 3.11. Укажи в `DATABASE_URL` строку подключения к отдельной тестовой базе PostgreSQL, где тесты смогут создавать схемы. Затем выполни `python -m unittest discover -s tests -v` и `python -m mypy --strict news_futures tests`. Для проверки в Chrome собери фронтенд (`npm ci` и `npm run build` из `frontend/`) и перед запуском тестов укажи путь к браузеру в `OPERATOR_TEST_CHROME`. При правке Decisions проверь ID во всех трёх шагах и отказ без подмены.
